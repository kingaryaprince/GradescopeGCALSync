## Why Docket needs Gradescope open in Chrome, exactly

- It needs a **live Gradescope session in the Chrome profile Docket is installed in**.
  `lib/gradescope/client.ts:34` fetches with `credentials: 'include'`, so it uses that
  profile's cookie jar. No tab has to be open.
- It needs **Chrome running** to notice changes. `background.ts` sets a `chrome.alarms`
  timer (`installAlarm`, default every 6 hours, first run 1 minute after start). Calendar
  reminders still fire with Chrome closed because Google sends them.
- The Calendar half uses `chrome.identity.getAuthToken`, which uses the Google account the
  Chrome profile is signed in to. That is a second, separate dependency: the Gradescope
  login and the Google account do not have to match, but both live in one profile.
- Not verified: how long the session lasts. CLAUDE.md says the cookie has no expiry and
  dies with the browser. Two things can keep it alive anyway: Chrome's "Continue where you
  left off" restores session cookies, and Gradescope's login form has a remember option.
  Check DevTools > Application > Cookies on gradescope.com for a cookie with an expiry
  date after logging in through CalNet.
- Gradescope has no API and no OAuth, so the login itself cannot be removed. What can be
  removed is the manual recovery and the guessing.

## What happens when the session expires

1. The next alarm runs `runSync`. `refreshCourses` throws `NotLoggedInError`.
2. `runSync` saves a failed report over the last good one (`background.ts`, the `catch`
   block). The time of the last successful sync is gone.
3. `updateBadge` replaces the count with a red "!". The deadline counts are hidden even
   though the cached list is still correct.
4. The popup shows the error as plain text. The "Sign in" link (`popup.ts:88`) only
   appears when the failure happens during a click, not for a background failure.
5. Recovery: open gradescope.com, sign in, come back, click Sync. Otherwise wait for the
   next alarm, up to 6 hours.

## Findings

### A. No "data as of" time
`storage.ts` saves `assignmentCacheAt` on every write and nothing reads it. `popup.ts:376`
shows the last sync as a time with no date, so "3:15 PM" can be three days old.
Fix: show "Deadlines as of Mon 3:15 PM" from `assignmentCacheAt`, always, and keep it on
screen when the last sync failed. Keep the badge count with the failure marker beside it.

### B. No automatic recovery after signing back in
Fix: in `background.ts`, when the last report failed with not-signed-in and a
gradescope.com tab finishes loading on a page that is not `/login`, run the sync.
`chrome.tabs.onUpdated` should expose the URL for gradescope.com through the existing
host permission, with no new permission; confirm that in Chrome before relying on it.
Then the whole recovery is "sign in to Gradescope", which he was about to do anyway.

### C. A course that fails to load drops out of the popup and the badge
`runSync` builds the popup cache from `readEntries`, the courses read this run
(`saveAssignmentCache(toCache(readEntries))`). `refreshDeadlines` does the same with
`entries`. Calendar events for a failed course are kept on purpose (the "deletion is
conservative" invariant), but the popup list and badge lose that course until the next
good run. Fix: carry forward the cached rows of selected courses that failed this run.

### D. The same failure causes a burst of "new assignment" notices
The grade snapshot is rebuilt from `readEntries` only. A course that failed once is
missing from the snapshot, so the next good sync sees every one of its assignments as
new. Only matters with new-assignment notifications on. Fix: merge into the old snapshot
for courses not read this run.

### E. Session expiring mid-run reports success
If the course list loads and every course page then bounces to login, each failure
becomes a warning, `report.ok` is true, and the cache is written empty. Fix: if every
selected course failed with `NotLoggedInError`, fail the run.

A to E are one change in `background.ts` plus tests in `tests/sync.test.ts` and
`tests/upcoming.test.ts`. A and B are the ones he would feel.

## F. Staying signed in (added 2026-11-16)

What the live account showed: Gradescope already sets a `remember_me` cookie that lasts
about 13 months (expiry 2027-12-21), `SameSite=None`, so it is sent with Docket's requests.
So "Chrome logs me out" most likely comes from one of two places:
1. Chrome deleting cookies when it closes (a setting, or an extension). Then `remember_me`
   is gone too, and no amount of Docket code fixes it. The popup now says so, with the
   fix: add `[*.]gradescope.com` under chrome://settings/content/siteData, "Allowed to
   save data on your device".
2. The session cookie expiring while `remember_me` survives. Docket now loads `/` once and
   retries before reporting "signed out", and records `recovered` when that works.

Built: the retry, a "Remembered sign-in: present/missing" line in Settings > Last sync
(new `cookies` permission, used only to read that one cookie's presence and expiry), and
auto re-sync on the next Gradescope page load. Not built: a saved password. CalNet's Duo
step makes it impossible for Berkeley, and email-login accounts are already remembered
for a year. Reasons in CLAUDE.md, Roadmap.
